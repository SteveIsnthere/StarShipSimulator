The exact observed32-sampler shader path and measured94.82% GPU query share justify one fixed width1 investigation. The proposed public renderer.limits.maxBatchableTextures assignment after awaited app.init and before layer/emission construction is preferable to spoofing hardware limits, changing packages or manipulating cached private shaders. Other actual backends/unknown strings remain untouched. Locked Pixi defaults take the public limit at DefaultBatcher creation, and ordinary batch iteration preserves element order while splitting texture groups. Actual linked uTextures[1]/direct sampling must prove lifecycle efficacy; a requested field is not enough because the default shader cache is global. A fresh single-application context and source-backed pre-first-batcher check are necessary. Production adoption also requires context-loss/restoration behavior: GlLimitsSystem resets the field on contextChange, so startup success is not persistence proof.

The acknowledged exact-state blocker is real. Historical three real callbacks advanced physical/camera/emitter state by wall-time-derived deltas. Changing throughput changes those inputs. Current flat telemetry, projections and aggregate particle inspection do not expose complete raw camera/pool arrays, and the historical browser is closed. Public debug methods cannot guarantee reconstruction of its exact44.232417m frozen state. Arbitrary delays, synthetic clocks, camera/private-pool writes or tolerance relaxation would falsify the claimed control.

The minimum trustworthy alternative is an explicitly declared NEW shared deterministic presentation fixture for original32 and candidate1. Use the actual production controller fixed-step/onStep-camera and scene draw/update functions with identical named DT inputs during fixture preparation, emitting/updating particles via their original code. Do not create manual particle substitutes or approximate physics. Freeze the resulting same source-owned state, then run ordinary RAF callbacks and the unchanged full-session/GPU probe for each20-frame diagnostic window. Compare exact complete physical inputs/projection/pool logical state and positive pixels between the original and candidate fixture. A fixture prepared by direct production draw/update calls is qualification setup, not original live-flight frame acceptance or a reproduction of old wall-conditioned inputs.

Prefer a research entry or small source-owned presentation fixture seam that calls the existing production functions. Do not add a player-facing product control or silently redirect the production clock. If state transfer is chosen instead, it must use an explicit complete source-owned serialization/restore contract for camera, emitter counters, particle arrays and backdrop/post clocks, not ad hoc writes to hidden objects; that is larger than a deterministic shared-input fixture. No current snapshot can retroactively supply omitted old arrays.

The exact fixture code/inventory/DT schedule and dual-source binding must be reviewed before applying a patch or qualifying a build. A newly qualified original32 fixture and identical candidate1 fixture preserve strict equivalence; retain historical controls as history rather than pretending their different physical inputs match. Keep actual hardwareMAX32, AA/DPR/viewport, all scene/material/plume/cloud/ground cues, original query completeness and exact physics limits. No width sweep or automatic fallback. A source-owned fixture or build bridge must explicitly allow only the batching candidate/fixture changes; old unchanged-renderer qualification cannot be silently reused.

After faithful equivalence and actual linked shader proof, propose one candidate attribution under the next independently reviewed bounded cycle.
