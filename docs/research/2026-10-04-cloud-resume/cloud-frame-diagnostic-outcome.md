# Single launch trace — cadence diagnosis, not acceptance

The parent reported the one approved desktop diagnostic exited 0, one test passed in 41.5 seconds. This proves diagnostic capture completed; the 30 measured frames do not satisfy the 300-frame acceptance floor, and tracing adds overhead. No browser rerun, graphics edit or performance acceptance followed this analysis.

All current HTML-report and test-result artifacts were copied before another run into `cloud-frame-diagnostic-artifacts/`; `sha256.json` covers every copied raw file and the analysis summary. Original trace SHA256: `1bc1edd31ca940487ad3fe4813219c4bc7d02056575fcbf353768e25f9733c67`, 23,670,394 bytes, 113,735 events. The stream reached EOF, no export cap was exceeded, no cleanup error occurred, and reported buffer usage stayed below 27%. Before/after source/build receipts match. The original probe, manifests, trace declaration, complete trace and buffer receipts are retained alongside their HTML-report attachments.

The probe identifies the actual `world-canvas` as canvas 3, WebGL2 through ANGLE/SwiftShader. Two distinct WebGL1 feature-detection canvases have no test ID. The capture completed 60 warmed and 30 measured drawn timestamps, with **zero no-draw timestamps**. Measured cadence was 3.124024 fps; aggregate RAF CPU mean 6.72 ms/p95 12.8 ms and completion-fence wait mean 0.046667 ms. These profiling-perturbed numbers cannot be compared as a fresh acceptance baseline.

The user-timing markers bound the measured trace phase to 9.683740 seconds. During that interval, 30 main frames deliver the three expected RAF callbacks per frame. A clipped boundary callback can appear in overlap counts; that is not an additional measured frame. Renderer-main `RunTask` occupies about 363.49 ms wall time, with 218.022 ms reported thread CPU. The GPU-main `RunTask` union occupies 9,683.054 ms of the 9,683.740 ms phase, with only 118.236 ms reported thread CPU. `GLContextEGL::MakeCurrent` occupies 7,258.797 ms clipped wall time, versus only 16.722 ms thread CPU; WebGL tasks occupy 2,359.225 ms wall time versus 44.23 ms thread CPU. These are nested event groups and **must not be added together**.

This establishes the critical path at the browser GPU service waiting on software GPU work, rather than missing drawn frames or the app's JavaScript simulation/scene updates taking hundreds of milliseconds. Two alternating EGL contexts share the traced surface, but the trace does not map their opaque IDs conclusively to world rendering versus compositor/raster clients. Individual shaders, bloom, UI compositing and native SwiftShader worker internals remain unattributed. The short reported finish-fence wait is therefore not proof that full browser GPU/compositor work is cheap.

The runtime has a four-core cgroup quota over five allowed CPUs. Across the whole before/after resource interval, CPU usage increased by 118.854284 core-seconds over 305 quota periods; 277 periods were throttled, and aggregate throttled time increased by 18.453315 seconds. Those samples include setup/warmup/measurement/trace collection, not just the measured phase. The quota-period/usage data shows the software-rendering workload saturated the available four-core budget. “No CPU throttling requested” means the test did not configure a DevTools slowdown; it does not mean the host cgroup was unthrottled.

Fresh independent review of the original raw trace agrees that GPU-service waits and software-renderer/quota saturation dominate the cadence failure. It rejects summing nested spans, blindly identifying EGL contexts with feature-probe canvases, or declaring expensive application shaders from the small RAF/fence samples. No production graphics change is justified by this trace alone. A next bounded environmental diagnostic would need an explicitly reviewed backend/worker-affinity hypothesis, unchanged rendering/scenario inputs and a new source-pinned receipt; this document does not authorize or claim that run.
